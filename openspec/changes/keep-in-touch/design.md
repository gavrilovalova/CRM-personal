# Design

## Context

- Данные: таблицы `contacts` и `notes` (`db/schema.ts`); у заметки есть `created_at`, есть индекс `(contact_id, created_at)`.
- Запросы к базе - в `db/queries.ts`, серверные действия форм - в `app/actions.ts`, проверка полей - zod-схема `contactInputSchema` в `lib/validation.ts`. Список полей формы (`CONTACT_FIELDS`) берётся из ключей схемы.
- Формы: добавление - `components/add-contact-dialog.tsx`, правка и просмотр - `components/contact-details.tsx`, текстовые поля - `components/contact-fields.tsx`. Выпадающего списка в `components/ui/` нет.
- Главная - `app/page.tsx`, шапка с логотипом и кнопкой «Добавить контакт».
- Автотестов в проекте нет; проверка - руками на локальной базе.
- Мотивация и решения владельца - см. proposal.md, поведение - specs/keep-in-touch/spec.md.

## Goals / Non-Goals

**Goals:**
- Правило «просрочен ли контакт» считается в одном месте - в SQL-запросе, по часам базы. Страница и счётчик берут его оттуда и не расходятся.
- Смена частоты и стартовая точка отсчёта сохраняются в одном запросе, без гонок.

**Non-Goals:**
- Уведомления, напоминания по почте, «отложить» контакт.
- История смен частоты.
- Автотесты и тестовый фреймворк (новая библиотека - только после обсуждения).

## Decisions

### 1. Два новых поля в `contacts`
- `touch_frequency` - enum Postgres `touch_frequency` (`week`, `month`, `quarter`, `year`), может быть пустым (= «Не задано»).
- `touch_frequency_set_at` - `timestamptz`, может быть пустым: когда частоту последний раз задали или сменили.

Почему enum, а не число дней: в интерфейсе ровно четыре варианта, enum не даст записать мусор. Длины в днях (7/30/90/365) живут в коде запроса одной таблицей соответствий.
Альтернатива - отдельная таблица «правила общения»: лишняя сложность для одного поля.

### 2. Стартовая точка и смена частоты - в SQL при сохранении
- `createContact`: если частота задана - `touch_frequency_set_at = now()`, иначе пусто.
- `updateContact`: `touch_frequency_set_at` пересчитывается выражением в том же `UPDATE`:
  если новая частота отличается от старой (`IS DISTINCT FROM`) - `now()` (или пусто, если частоту убрали), иначе остаётся как было.
  Так повторное сохранение формы с той же частотой не сбрасывает отсчёт (требование «Правка других полей не сдвигает отсчёт»), и не нужно отдельно читать старое значение.

### 3. Запрос «кто просрочен» - один, с подсчётом дней в базе
`listOverdueContacts()` в `db/queries.ts`:
- последняя заметка - `max(notes.created_at)` по контакту (подзапрос/`LEFT JOIN ... GROUP BY`, использует существующий индекс);
- стартовая точка - `coalesce(последняя заметка, touch_frequency_set_at)`;
- прошло суток - `floor(extract(epoch from now() - старт) / 86400)`;
- срок - `CASE touch_frequency WHEN 'week' THEN 7 ...`;
- фильтр: частота задана и прошло суток `>=` срок;
- сортировка: (прошло - срок) по убыванию, затем имя `collate "ru-x-icu"` и `id` - как в основном списке.
Возвращает id, имя, частоту, число суток и признак «есть заметки».
`countOverdueContacts()` - тот же подзапрос с `count(*)`; общий кусок SQL выносится в одну функцию, чтобы правило не раздвоилось.

Почему в базе, а не в JS: `now()` один для всех браузеров и не зависит от часового пояса компьютера; сортировка и фильтр не тянут всех людей в память.

### 4. Форма: поле выбора через shadcn `select`
- Добавить компонент `components/ui/select.tsx` (план - командой `pnpm dlx shadcn@latest add select`; реестр оказался недоступен, файл собран вручную в том же стиле) - это файл компонента поверх уже установленного `radix-ui`, новой зависимости в `package.json` не появляется (проверить при добавлении; если появится - остановиться и спросить).
- Radix Select с `name="touchFrequency"` отдаёт значение в `FormData`, серверное действие читает его как остальные поля.
- React после каждой отправки формы сбрасывает её поля к начальным значениям, и скрытый системный `<select>` внутри Radix откатывал выбор. Поэтому поле хранит значение в своём состоянии и пересоздаётся с отправленным значением (`key` по значению из `state.values`) - так же, как остальные поля получают введённое через `defaults`.
- Пустое значение Radix не принимает, поэтому «Не задано» передаётся значением `none` и в zod превращается в `null`.
- В `contactInputSchema` - поле `touchFrequency: z.enum([...,"none"]).transform(...)`; тогда `CONTACT_FIELDS`, ошибки и «запомнить введённое при ошибке» работают без особых случаев.
- Новый компонент `TouchFrequencyField` ставится в `ContactFields` после «Откуда знакомы». Подписи вариантов и словарь `week → «Раз в неделю»` - в `lib/touch-frequency.ts`, общий для формы, карточки и страницы.
- Просмотр карточки: строка «Как часто общаться» в `ContactDetails`.

Альтернатива - нативный `<select>`: проще, но выглядит иначе, чем остальные поля shadcn.

### 5. Страница `/keep-in-touch` и ссылка в шапке
- `app/keep-in-touch/page.tsx` - серверный компонент: шапка с «← Все контакты», заголовок «Пора связаться», список строк (аватар `ContactAvatar`, имя, частота, подпись про дни) или пустое состояние. Загрузка - в `Suspense` со скелетоном, как на карточке.
- Подпись дней собирается через существующий `formatCount(n, ["день","дня","дней"])`.
- В шапке `app/page.tsx` - серверный компонент `KeepInTouchLink` в своём `Suspense` (запрос счётчика не задерживает список); число - через `Badge`. Цвета и отступы - только токены.

### 6. Обновление после изменений
В `app/actions.ts` добавить `revalidatePath("/")` и `revalidatePath("/keep-in-touch")`:
`addNote` (сейчас обновляет только карточку), `createContact`, `updateContact`, `deleteContact`.

## Risks / Trade-offs

- [Время базы и время сервера приложения разные] → все расчёты «сколько прошло» только через `now()` базы; даты в JS не сравниваем.
- [Radix Select внутри формы в диалоге: значение по умолчанию после ошибки валидации] → передавать `defaultValue` из `state.values`, проверить руками сценарий «ошибка в почте - выбранная частота не слетела».
- [Нет автотестов на правило просрочки] → в задачах - ручная проверка граничных случаев сдвигом дат в локальной базе (SQL ниже в tasks.md).
- [Миграция на проде] → только добавляет nullable-колонки и enum, без перезаписи данных; выполняется отдельным шагом до старта нового образа, как принято.

## Migration Plan

1. `pnpm db:generate` - миграция `drizzle/0001_*.sql`: `CREATE TYPE touch_frequency`, `ALTER TABLE contacts ADD COLUMN touch_frequency`, `ADD COLUMN touch_frequency_set_at`.
2. Выкатка обычным путём: merge → образ → миграции → новый образ → smoke `/health`.
3. Откат: старый образ не знает о новых колонках и спокойно работает с ними; откат вручную, владелец запускает сам. Удалять колонки при откате не нужно.
